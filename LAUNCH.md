# Launch checklist

1. For a **new, empty** Supabase project, run these files in the SQL Editor, one at a time and in this order: `supabase/schema.sql`, `supabase/launch-hardening.sql`, `supabase/variant-inventory.sql`, `supabase/access-control.sql`, `supabase/order-status-inventory.sql`, `supabase/20261026-production-hardening.sql`, `supabase/20261027-fix-checkout-digest.sql`. Create the first administrator in Supabase Auth and set that user's `profiles.role` to `admin` immediately before `access-control.sql`; that migration promotes the legacy administrator to the protected `owner` role. For an **existing** store, inspect the deployed function definitions and database objects first, then apply only the missing migrations in dependency order. Do not rerun `schema.sql` against a live store or assume filename order alone proves migration state. Back up the database before approved changes.

   Before `20261026-production-hardening.sql`, run `select to_regprocedure('extensions.digest(text,text)');` and proceed only if it returns the pgcrypto function. The checkout migration expects pgcrypto in Supabase's `extensions` schema.
2. Deploy `supabase/functions/storefront` with JWT verification disabled because checkout/contact requests are public and it performs its own validation. Deploy `supabase/functions/manage-access` with the default JWT verification enabled; it also verifies the current user and Owner role inside the function before using its service-role client. The service-role key remains in Supabase secrets only and must never be placed in a browser file.
3. Set the Edge Function secret `PUBLIC_SITE_URL` to the exact deployed HTTPS origin, for example `https://shop.example.com`. Set `ALLOWED_ORIGINS` to a comma-separated list of allowed browser origins, for example `https://shop.example.com,http://localhost:5500` while developing locally. Set a long, random `THROTTLE_PEPPER` secret; it is required for server-peppered checkout/contact throttling. `PUBLIC_SITE_URL` is also the CORS fallback origin.
4. Configure Supabase Auth: enable email confirmation, set the production Site URL and redirect allow-list, enable MFA for every Owner, and set a strong password policy.
5. In the live admin panel, sign in as the Owner and open **Access control**. Create each employee directly using the email and individual password provided on paper, then select a preset or custom role. No invitation or reset email is sent. One role can be assigned to many employees, and every employee has a separate password. The password is stored by Supabase Auth and cannot be viewed after saving; use **Set password** to replace it when needed.
6. For Vercel, deploy the repository's `vercel.json` security headers and check the resulting response headers on every HTML route. `_headers` is retained for hosts that support it. Force HTTPS and attach your custom domain.
7. Upload the missing product and slideshow images before publishing. Do not use customer image data URLs as a long-term image store; use Supabase Storage with a restricted upload policy.
8. Test: customer order, same-request retry (one order only), invalid coupon, out-of-stock order, two simultaneous orders for the same low-stock product, cancellation then reactivation, contact form spam, customer login, Owner login, fulfillment-role login, role change, direct employee creation, direct employee password change, logout, and mobile checkout.
9. Run the read-only `supabase/checkout-contract-diagnostics.sql` in Supabase SQL Editor. Confirm RLS is enabled; direct `orders`, `checkout_requests`, and `submission_throttle` grants are absent for `anon` and `authenticated`; the intended RPC grants exist; `active_owners` is at least one; and the variant stock mismatch query returns no rows.

## Before accepting real card payments

Replace the `Card (demo)` option with a hosted checkout from an approved payment provider. Never collect, transmit, or store raw card numbers in this project.
